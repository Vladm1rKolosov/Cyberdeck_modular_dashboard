# Архитектура и функциональные блоки CYBERDECK

## Принятое направление

Референс хорошо работает как компактный телеметрический HUD, но его горизонтальная трёхколоночная композиция не подходит целевому портретному экрану. В CYBERDECK сохранены визуальные принципы Red Alert: почти чёрный фон, основной красный `#ff3344`, тонкие рамки, свечение только у активных данных, моноширинная типографика, сетка и CRT scanlines. Компоновка перестроена под 1080×1920.

Стек MVP:

- Python 3.11+ и FastAPI — локальный сервер, интеграции и защита секретов;
- `psutil` и системные утилиты — телеметрия Windows;
- WebSocket — поток обновлений;
- HTML/CSS/JavaScript без сборщика — минимальный порог запуска;
- JSON + localStorage — профиль и пользовательская раскладка.

UI не должен знать, откуда пришла метрика. Сервер приводит каждый источник к стабильной схеме, а виджет только отображает данные. В дальнейшем клиент можно перевести на React/GridStack без изменения интеграций.

## Какие блоки стоит организовать

### Уровень 1 — постоянно видимые

1. `System status`: время, дата, hostname, uptime, питание, состояние telemetry bridge.
2. `CPU`: общая загрузка, частота, загрузка логических ядер, позже температура.
3. `GPU`: загрузка, температура, VRAM, мощность; при отсутствии сенсора блок деградирует корректно.
4. `RAM`: процент, занято/всего.
5. `Network`: download/upload и состояние связи.

Это наиболее полезная информация для фонового экрана: она читается за несколько секунд и не требует взаимодействия.

### Уровень 2 — обзор по запросу

6. `Storage`: заполнение томов; обновлять редко, не каждую секунду.
7. `Processes`: top по памяти/CPU; обновлять раз в 5–10 секунд.
8. `Calendar / Focus`: следующая встреча, текущая задача, таймер фокуса.
9. `Media`: текущий трек и управление; показывать только при активном проигрывателе.
10. `Notifications`: агрегированный список событий, а не сырой поток Windows.

### Уровень 3 — специализированные модули

11. `Dev Sentinel`: локальные порты, Git-ветка, CI, Docker/WSL.
12. `Weather / RSS / Currency`: отдельные провайдеры с кэшем и ограничением частоты запросов.
13. `Safe actions`: только заранее объявленные команды (например, открыть приложение или запустить конкретный скрипт). Произвольный терминал из обоев добавлять нельзя.

## Модель модуля

Каждый виджет должен иметь:

- уникальный `id` и стабильный `type`;
- заголовок, размер, позицию и видимость;
- настройки отображения;
- имя источника данных и интервал обновления;
- состояния `loading`, `ready`, `stale`, `error`, `unsupported`;
- контракт данных с версией.

Провайдеры данных должны работать независимо: сбой Spotify или погоды не останавливает системную телеметрию.

## MVP

Текущая версия покрывает первый вертикальный экран, реальные системные данные, WebSocket, Red Alert UI, изменение порядка и размеров, дублирование/скрытие, экспорт/импорт.

Следующий минимально полезный инкремент:

1. серверное сохранение нескольких профилей;
2. каталог для возврата скрытых и добавления новых виджетов;
3. разные частоты опроса для быстрых и медленных метрик;
4. температуры через LibreHardwareMonitor/OpenHardwareMonitor bridge;
5. автозапуск Python-службы и готовый профиль Lively Wallpaper;
6. календарь как первая OAuth-интеграция.

## Основные риски

- Wallpaper Engine может не передавать мышь обоям, пока не включено взаимодействие; Edit Mode лучше открывать в обычном браузере или отдельном окне настроек.
- Температуры CPU/GPU не имеют единого надёжного Windows API. Для полного мониторинга потребуется LibreHardwareMonitor либо HWiNFO shared memory.
- Частые PowerShell/WMI-вызовы создают нагрузку. Их надо кэшировать и выполнять с разными интервалами.
- OAuth callback неудобен внутри движка обоев. Авторизацию следует проводить в обычном браузере, а токен хранить на backend.
- Wallpaper Engine может приостанавливать страницу при полноэкранной игре. Сервер должен прекращать или сильно замедлять сбор, если клиентов нет.
- Любая команда из UI — граница безопасности. Разрешён только allowlist, привязанный к localhost; произвольный shell endpoint запрещён.
- Код визуального референса не стоит копировать как основу: он жёстко связан с конкретной разметкой и горизонтальной компоновкой. Полезнее перенести дизайн-токены и поведенческие идеи.
